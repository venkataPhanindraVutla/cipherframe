# 0033. Integrity design

- Status: Accepted
- Date: 2026-11-12
- Gate: P9
- Deciders: project owner (the manifest outline in the last section is flagged for owner review)

## Context

M5 signs an integrity manifest for each asset and a record for each deletion. Pitfall 1 requires
that verification never needs the signing secret. The plan fixes SHA-256 per artifact (M5-1) and
signing keys with key IDs and rotation (M5-2). It leaves open the Merkle construction, the canonical
encoding, the signature format and where the signing keys are kept.

## Options considered

- Merkle: an RFC 9162 tree; a flat list of hashes; a custom binary tree.
- Encoding and signature: JCS with a DSSE envelope and Ed25519; JCS with a detached JWS (EdDSA);
  JCS with a raw Ed25519 signature.
- Key custody: keys wrapped by the KMS and used to sign in-process; signing inside the KMS.

## Decision

**Hashing and trees**

- SHA-256 for every artifact, computed while streaming (pitfalls 3 and 10).
- Merkle trees use RFC 9162 (Certificate Transparency v2) hashing: a leaf is
  `SHA-256(0x00 || data)`, an interior node is `SHA-256(0x01 || left || right)`, and unbalanced
  trees are handled as the RFC specifies. Inclusion proofs follow RFC 9162, which serves the
  per-segment proof endpoint (M5-3).
- There is one tree per rendition, whose leaves are the init segment then the media segments in
  playlist order, each leaf's data being that artifact's SHA-256. A top-level tree combines the
  rendition roots with the hashes of the other artifacts, in a fixed order that the manifest
  records.

**Encoding and signature**

- Documents are JSON in canonical form per RFC 8785 (JCS).
- They are signed as **DSSE** envelopes with **Ed25519**, with a `keyid` on each signature. The
  payload types are `application/vnd.cipherframe.manifest+json` and
  `application/vnd.cipherframe.deletion+json`. DSSE's pre-authentication encoding provides domain
  separation, and an envelope can carry more than one signature during a key rotation.

**Signing keys**

- Ed25519 private keys are generated by Cipherframe and stored wrapped by the configured KMS, using
  the same envelope scheme as content keys, with AAD bound to the purpose and key ID. The worker
  unwraps a key and signs in-process. This works the same way with the local, Vault, AWS and GCP
  providers.
- Several verification keys can be active at once, and they are published at
  `/.well-known/cipherframe-keys.json` (M5-2). A retired key stays published so that old records
  still verify.

**Manifest outline (for owner review; the exact fields are fixed in M5-1)**

- `schema` (`cipherframe.manifest/v1`), asset ID, tenant ID, creation time, pipeline version.
- The encoder settings and the FFmpeg version string.
- Per rendition: its name, resolution, bandwidth, segment count and Merkle root.
- Other artifacts: the master playlist, the media playlists, and later the subtitles, thumbnails
  and so on, each with its kind, path within the asset and SHA-256.
- The top-level root, and a reference to the source hash recorded at ingest. The source object
  itself is never published (I4).

## Consequences

- A verifier needs only SHA-256, Ed25519, JCS and DSSE, all of which have standard implementations,
  plus Cipherframe's published public keys.
- A compromised worker exposes the active signing key. Rotation with key IDs limits how long a
  stolen key is useful, and a key that is revoked can be marked so in the published key set.
- Signing inside the KMS remains possible later as an additional key type.
